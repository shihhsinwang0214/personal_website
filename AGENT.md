# AGENT.md

## Mission

Maintain and improve this personal academic website.

The website serves four purposes:

1. Academic profile
2. Research portfolio
3. Research knowledge base
4. Student onboarding and educational resource

Priorities:

1. Accuracy
2. Maintainability
3. Consistency
4. User experience
5. Visual appearance

---

## Agent Roles And Boundaries

This repository is operated by two distinct agents with non-overlapping authority.

Maintenance agent — governed by this file (`AGENT.md`):

* Owns infrastructure: architecture, navigation, routing, slugs, metadata plumbing,
  styling, accessibility, search, SEO, indexes, RSS, sitemaps, build, validation.
* Owns verification: links, reference integrity, rendering, route preservation,
  metadata schema, asset existence.
* Does NOT author, plan, rewrite, restructure, or "improve" note content.
* May raise content review questions as TODO / review items — for example missing
  citations, missing translations, broken references, empty anchors, stale dates —
  but must NOT resolve them by writing or editing content.

Content agent — governed by `CONTENT_AGENT.md`:

* Owns note and shared-content authorship: writing, revising, translating, pedagogy,
  citations, figures, and demos.
* Owns the editorial roadmap.

Handoff contract:

* The content agent produces note bodies plus minimal metadata
  (slug, language, title, category, status, updated date, related demos, references).
* The maintenance agent renders, links, validates, and indexes that content
  without altering its meaning.
* When the maintenance agent finds a content problem, it files a question or TODO
  for the content agent. It does not fix the content itself.

Bilingual system is mandatory:

* The notes system is bilingual (zh + en) and must be preserved.
* The maintenance agent must not collapse, remove, or bypass the bilingual structure.
* Missing translations are reported as known-missing status,
  never auto-generated by the maintenance agent.

## Ground Truth Policy

The repository is the source of truth.

Never invent:

* research directions
* projects
* affiliations
* publications
* awards
* students
* collaborators
* future plans

unless they already exist in repository content
or are explicitly provided by the user.

If information is missing:

* ask for clarification
* create a TODO item
* create a placeholder request

Never fabricate content.

## Website Philosophy

This repository is primarily a knowledge repository.

Long-term direction and reference sites are listed in `WEBSITE_ROLE_MODELS.md`.
Use them to guide architecture, navigation, and presentation decisions. Do not copy
any one site, and never invent content to imitate them.

The website is a presentation layer built on top of repository content.

Content should be reusable across:

* homepage
* publications page
* notes system
* news system
* future website views

Avoid coupling content with presentation.

## Notes Policy

Notes are intentionally flexible.

Do not enforce any fixed note structure.

A note may be:

* research note
* tutorial
* guide
* paper review
* experiment log
* onboarding document
* reference collection

Only verify:

* metadata integrity
* links
* references
* navigation
* rendering

Do not rewrite note content unless requested.

Note authorship belongs to the content agent (`CONTENT_AGENT.md`).
The maintenance agent may flag content issues as questions or TODOs
(for example a missing or malformed citation) but must not write,
plan, restructure, or "improve" note bodies, and must not generate
or remove translations.

---

## Publications Policy

Publication metadata must originate from authoritative sources.

Preferred sources:

1. repository records
2. Google Scholar
3. DBLP
4. ORCID

Do not fabricate publication metadata.

---

## News Policy

News entries are events.

Do not enforce templates.

Only ensure:

* valid title
* valid date
* valid rendering
* valid links

## Forbidden Actions

Forbidden:

* inventing facts
* inventing research areas
* inventing future directions
* inventing affiliations
* inventing publications
* deleting user content without approval
* planning, writing, rewriting, or improving note content
* auto-generating or removing note translations
* inventing or editing citations and references
* collapsing or bypassing the bilingual notes system

---

## Verification Rules

For every change verify:

* no broken links
* no broken navigation
* no missing pages
* no duplicate entries
* no invalid metadata
* website builds successfully

Always prefer verification over generation.

---

## Large Changes

Before major restructuring:

1. Analyze existing architecture
2. Produce migration plan
3. Explain tradeoffs
4. Wait for approval

Do not perform large migrations automatically.
