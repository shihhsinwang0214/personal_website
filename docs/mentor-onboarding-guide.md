# Mentor 指南：帶一個新人的第一個月

給主要 mentor 與備援 mentor 看的。**不上站**——網站上的 [新人上手] 那一區是純粹寫給學生的，
這份是對應的另一半：學生那邊每個階段的產物與門檻，mentor 這邊要提供什麼。

來源：`docs/mentoring-first-month-draft.md`（完整草稿）。

## 開始之前

**角色要有人**。第一次一對一時把這張表填完；可以一人兼多職，但不能有空格。

| 角色 | 誰 | 責任 |
|---|---|---|
| 指導教授 / PI | | 研究問題空間、品質標準、重大方向決策 |
| 主要 mentor | | 選起始任務、示範、主持 checkpoint 與回饋 |
| 備援 mentor | | 主要 mentor 不在時的判斷與轉介 |
| 技術支援 | | 環境、程式、資料、運算資源 |
| 日常求助頻道 | | 一般問題與轉介（填實際 Slack 頻道） |
| 敏感／衝突事項聯絡人 | | 不適合公開或直接向 mentor 反映的問題 |

**起點盤點**：相關的數學／程式／Git／Linux／領域背景、是否做過論文閱讀與結果重現、可投入時間與資源、
對公開提問的舒適程度、帳號權限是否就緒。只用來決定從哪一層鷹架開始，不推論能力上限，也不拿來篩選。

**Start Here 清單**（不超過五項）：核心材料 / 任務工具 / 延伸材料 / 暫時不讀。

**起始任務**要事先確認：目標結果、參考環境、合理誤差、預估執行時間、運算預算、已知失效模式、停止條件。
最常見的失敗是新人把第一個月耗在無法診斷的基礎設施問題上。

## 逐步放手的五級

自主不是從「完整答案」直接跳到「沒有提示」。每一項能力依序調整支持：

1. mentor 完整示範一次，說出決策理由、常見岔路與檢查方法；
2. 新人完成部分步驟，mentor 保留關鍵決策提示；
3. 新人選擇方法，mentor 只保留檢查清單與中間 checkpoint；
4. mentor 只提供問題邊界、資源限制與品質標準；
5. 新人在新情境中建立流程、辯護決策並對結果負責。

責任是否增加由**產物與能力證據**決定，不由日期自動觸發。同一時間，一個人可能已能獨立處理環境問題，
卻仍需要示範理論判斷；遇到新工具或共同瓶頸時，退回更多提示是正常的。

## 各階段 mentor 要提供什麼

| 階段 | mentor 提供 | 學生產物（門檻） |
|---|---|---|
| 一、共同語言（第 1 週） | 從具體問題或既有結果開始；完整示範一次縮小版研究循環（含錯誤與修正）；帶過程式架構、實驗流程、主要指標與 failure log；標明核心／工具／延伸／不讀 | 環境 smoke test、一頁問題地圖、求助對象清單 |
| 二、重現（第 2 週） | 從已檢查過的基準實驗或既有結果中選一個，具備已知參考輸出、可接受誤差、合理執行時間、可診斷的失效方式 | 重現紀錄、差異表、一頁推理備忘錄 |
| 三、最小問題（第 3 週） | 一起比較 2–3 個候選方向，依重要性、可驗證性、資訊量、成本與風險收斂；回饋實驗卡 | 修訂後的實驗卡、一次最小實驗、可解讀結果或阻礙分析 |
| 四、說明與修正（第 4 週） | 維持判準；把回饋分成補證據／質疑解釋／建議轉向三類 | 修訂備忘錄、群組報告、下一步決策與理由 |

沒到門檻時的處理順序：**縮小任務 → 補一個 worked example → 恢復最近移除的一層提示**。
不要只是要求讀更多材料，那通常會讓情況更糟。

## Checkpoint 協定

- 每次 checkpoint 至少確認：上次之後做了什麼、學到什麼（含失敗）、現在卡在哪、下一步、需要什麼協助。
- 回饋要分類講清楚：這是肯定、指導，還是評價。
- 較嚴厲的回饋一律私下給；公開場合以提問、肯定、委婉建議為主。

## 需要往上反映的訊號

- 連續兩次 checkpoint 都停在同一個障礙，而且原因不明；
- 新人重複表示不知道找誰、或不敢問；
- 起始任務反覆卡在基礎設施，超過一週；
- 任何倫理、安全、資料使用或人際上的疑慮。
